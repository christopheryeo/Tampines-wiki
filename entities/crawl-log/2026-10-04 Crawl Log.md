#### Lessons learned

- **A genuine Singapore-nexus hit can come from an unexpected domain (export-control/national-security
  enforcement), not just defence-exercise or diplomatic coverage.** Every prior daily run's Singapore-
  nexus keyword scan surfaced only false positives (tax treaties, school-district acronym collisions,
  trade visits). Today's single genuine hit — a DOJ chip-smuggling indictment naming Singapore as a
  transshipment route — is a reminder that the nexus bar should stay content-based (does Singapore
  appear as a substantive party to the development) rather than narrowing informally toward
  defence/diplomatic framing only.
- **`ingest_cascade.py`'s own topic-routing (issue-tag keyword matching) can silently diverge from the
  topic a human operator judged correct and preserved via `--preserve-topic`.** `--preserve-topic`
  only protects the enrichment step's `topic:` field from being overwritten with the first issue tag —
  it does not make `ingest_cascade.py` honor that field when choosing which topic(s) to link in
  Coverage. The Step 10.5 backlink-verification gate caught this correctly this run (as designed), but
  the underlying mismatch is reproducible: any accepted candidate whose best-fit canonical topic uses
  vocabulary not present in its own issue tags (here, "Euro-Atlantic Security" vs. tags "Airspace
  Sovereignty, Drones, Missiles, Moldova, Russia") will cascade without its intended topic backlink by
  default and need a `patch_coverage.py` repair every time.
- **`--apply-assessment` has now been shown to silently drop two different preserve flags
  (`--preserve-topic`, fixed in PR #43; `--preserve-outlets`, found and fixed this run) via the same
  root cause: `apply_assessments()` re-implements the update path instead of calling the same code path
  `process_one()`/`--apply` uses, so any future flag added to `apply_result()` must be remembered twice.**

#### Recommendations to improve the topic crawl plan

- **Evidence:** `scripts/enrich_radar_inputs.py`'s `apply_assessments()` (the `--apply-assessment`
  code path) calls `apply_result(path, lines, body, assessment["consensus"], preserve_topic)` without
  an `existing_outlets` argument, while the live `--apply` path (`process_one()`) correctly passes
  `existing_outlets = metadata.get("outlets") if args.preserve_outlets else None`. Today's run hit this
  directly: both multi-outlet consolidation notes normalized this run had their verified 2-outlet
  `outlets`/`countries`/`coverageCount` silently collapsed to a single outlet the moment
  `--apply-assessment` ran (needed for the FP-9 note's unrelated category policy resolution, applied in
  the same combined-batch invocation covering all 8 notes).
- **Recommended change (implemented this run — see PR below):** add a `--preserve-outlets` flag to the
  `apply-assessment` subcommand's argument parsing already present for `--preserve-topic`, thread
  `existing_outlets` through `apply_assessments()` into `apply_result()` exactly as `process_one()`
  does, and add a regression test asserting a 2-outlet consolidation survives an `--apply-assessment`
  pass.
- **Expected accuracy benefit / API-call reduction:** prevents silent data corruption of verified
  multi-outlet corroboration (an operator-judged, source-verified fact) on every future run that
  combines a multi-outlet consolidation with any policy-resolved article in the same `--apply-assessment`
  batch — a combination this run shows is not rare (it occurred on the very first run where both
  conditions coincided). No API-call reduction (this is a correctness fix, not a recall/precision or
  cost change); the regression test adds negligible CI time and spends zero live API calls.
