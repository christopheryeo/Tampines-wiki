#### Lessons learned

- **The Oct-06 to Oct-07 topic-checkpoint gap indicates the "bulk-run exception" write path may not
  always land in the live, Dropbox-synced vault.** `entities/topic/` is gitignored and exists only as
  local filesystem state, not version-controlled state. Every one of the 96 active topic notes in
  *this* environment still showed a 2026-10-06T~19:3x:xxZ `lastCrawledAt` at the start of this run,
  despite the 2026-10-07 Crawl Log explicitly recording "all readback-validated... 96/96 Completed
  with today's lastCrawledAt" for that date. Two explanations are consistent with the evidence: (a) a
  Dropbox sync race genuinely dropped the Oct-07 write across all 96 files (the exact risk the plan's
  "Readback-validate every status write" clause already warns about), or (b) the Oct-07 session's
  bulk-close script ran against a *different* filesystem copy of this repository (e.g. an isolated
  sandbox or worktree) whose `entities/topic/` mutations never propagated back to this Dropbox-mounted
  path, since that directory carries no git history to reconcile divergent copies. Either way, a
  crawl log's self-reported "readback-validated" claim is not sufficient evidence that the *next* day's
  session will see the same state — this run's own pre-flight check (reading `lastCrawledAt` fresh
  from every active topic note before trusting any prior day's claim) is what caught the gap. Worth
  adding to the plan: before Step 1 freezes checkpoints, independently re-verify the previous run's
  claimed closure against the live notes rather than trusting the prior day's Crawl Log entry at face
  value.
- **A topic's own relevance-classification keyword list is unsafe to reuse verbatim as a SET A pass-2
  discovery query when the topic is Singapore-institutional.** See the Recommendations section below —
  this is the evidence basis for today's plan change.

#### Recommendations to improve the topic crawl plan

**Applied this run.** `scripts/topic_crawl_plan.md`'s Step 3 "High-volume recall rule" gained a new
required sub-rule: Singapore-institutional canonical topics (`mindef-governance`,
`republic-of-singapore-navy`, `republic-of-singapore-air-force`, `singapore-us-defence`, and any future
topic naming one specific Singapore institution) must run their SET A pass-2 query using only their
Singapore-specific terms first, not the full relevance-classification keyword list from
`topics/canonical-topics.yaml`. That list mixes genuine Singapore-specific terms with generic global
terms kept for classifying already-fetched text, and the generic terms alone (`naval`, `frigate`,
`warship`, `defence minister`, `ministry of defence`) push `totalResults` for these specific topics past
the 500-candidate ceiling on an ordinary day, pushing the whole topic into "high-volume/untriaged" and
silently discarding genuine Singapore coverage underneath global noise. **Evidence:** both the
2026-10-07 and 2026-10-09 daily runs independently marked the same four topics high-volume on their full
keyword-array query; narrowing to Singapore-specific terms only on 2026-10-09 reduced `totalResults`
from 792/4537/1415 to 12/1/13 for `mindef-governance`/`republic-of-singapore-air-force`/
`republic-of-singapore-navy` respectively, bringing three of the four back under the ceiling for full
triage in the same run (no accepted articles resulted today, but the topics were no longer silently
skipped). **Expected accuracy benefit:** these four topics will no longer be reflexively excluded from
triage on days when genuine Singapore-specific coverage exists but is masked by generic-term volume.
**Expected OpenAI API-call reduction:** none directly (this is a NewsAPI.ai SET A query change, not an
enrichment change); the four extra narrow queries added today cost 4 provider calls against a budget of
166, and prevent wasted enrichment calls on misclassified high-volume noise in the rare case a narrow
re-query surfaces a false positive (as happened once today, correctly dropped before enrichment).
